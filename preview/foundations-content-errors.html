These principles apply to every error in the product. Layout and behavior are in Error states. For capitalization and punctuation, refer to Content guidelines.

What a good error message does

A good error tells someone three things, in this order: what happened, why (when it helps), and what to do next. Everything else is decoration.

What happened
Name the thing that went wrong, in the person’s terms.
Couldn’t connect to Salesforce
Why
Give the reason when it helps them act. Skip it when it doesn’t.
The password for this account has expired.
What to do next
A specific step they can take, led by a verb.
Update the password in Accounts, then try again.
Name the specific thing
Couldn’t read dataset 4821 beats Read error. Include the name, ID, or value that failed.
Write as a person would, not as a system
Use couldn’t, isn’t, and doesn’t. Avoid invalid, illegal, exception, and failed on its own.
Make the next step doable
Lead with a verb: Check the schema name and try again. If there’s nothing the person can do, say what happens next, or who to ask and what to ask for.
Never blame the person
Write Enter a name, not You forgot to enter a name. Talk about what the system needs, not what they did wrong.
Say what you know
Something went wrong and An unexpected error occurred tell people nothing. If you only know what you were doing, say that.
Stay calm
No exclamation points, no Oops, no jokes. Apologize only when we’re at fault and the person has lost something. Use please only when our system is at fault and you need them to act.
Reassure when their work is safe
If nothing was lost, say so: Your changes are still here. If something was lost, say that too.
Put codes and IDs last
Request IDs and codes help support, but they’re not the message. Place them after the plain-language text.
Make it work on its own
A screen reader might read the message without its field or heading. Write Name is required, not Required.

Snap error messages

Errors in the new UI (Monitor, Admin Manager, and AutoSync) are designed by UX and live in Figma. Snap error messages are written by the Snap team, and the platform shows three strings together. The principles above apply in full. These rules cover the format.

Error
What happened. Can name the entity.
Couldn’t read dataset %s
Reason
Why it happened. Can come from the endpoint, or mix our text with the endpoint’s.
No dataset with ID %s exists
Resolution
What to do next.
Check the dataset ID and try again
Write the three strings as one set
They’re read together, in order, and must fit on screen without scrolling. Don’t repeat the error as the reason. The reason adds information.
Write fragments with no end punctuation
The SnapLogic Platform appends a semicolon (;) after each string automatically.
Let placeholders carry the specifics
Keep the wording reusable, and use %s so the displayed message names the dataset, schema, or value that failed.
Quote messages from other systems
Keep the endpoint’s own words as the reason: “Bad Gateway” error.
Name the setting, not “configuration”
Every problem with a Snap’s settings is a configuration error, so Snap configuration error says nothing. Say which setting and what it needs.
Start new strings with “Couldn’t”
It’s plainer than Unable to. Leave existing Unable to strings alone unless you’re already editing them.

When the error string is cryptic

Sometimes all you have is something such as Dn error. Write for the person, not for the log. To suggest a better message:

  1. Review the reason and resolution strings for clues. A reason of “Dn is null” with a resolution of “Please try with a non-null value” tells you a null value is in the wrong place.
  2. Search for the error string online. Here, you would find that “Dn” can refer to the descriptive name of a user or system on a network. Compose the message accordingly.
  3. Reach out to your Dev and QA contacts and verify that the message is accurate.
  4. Read the final message as someone who has never seen the system. Does it say what happened and what to do?
