Push drawer
Push drawer

Pushes the page over to make room. Nothing is covered; the page keeps working.

Use alongside the page
  • Details about something selected on the page
  • Follows the user as they click around
  • Can stay open like a reference

Run details · lint results · patterns catalog · MCP servers

Never float a panel over the page without a scrim. Covered content is blocked (overlay). Usable content moves over (push). Existing no-scrim panels that cover the page migrate to push drawers.

Which one

Work down the list and stop at the first rule that applies.

  1. Does the user need the page and the drawer at the same time — clicking rows, comparing, scrolling behind it? → Push
  2. Is it one task that must be finished or abandoned, with a Save / Create / Continue action, where half-finished state isn't valid? → Overlay
  3. Is it opened by selecting an object on the page (a row, a node, a card)? → Push. Opened from a toolbar or menu to start something new? → Overlay
  4. Would the user keep it open across several actions, or open it many times in a session? → Push
  5. Still unsure: read-mostly content → Push. A form that commits → Overlay

Tiebreakers
  • Width: content needing more than 720px or a two-column body → overlay. Push caps at 720 and every pixel comes out of the page.
  • Small workspace: under 960px there isn't room for both → overlay, always.
  • Stacking: a push drawer may open an overlay drawer or modal on top (a confirm, a sub-task); the scrim covers the push drawer too. Never stack two overlay drawers.
  • When both fit, choose push. It keeps the user's context and never traps them mid-task.
